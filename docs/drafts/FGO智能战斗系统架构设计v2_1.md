# FGO 智能战斗系统架构设计文档 v2.0

> **定位**：顶尖玩家级战斗代理的完整架构设计，不涉及具体编程实现。  
> **核心升级**：从"回合内规则 AI"升级为"整场路线 AI"。  
> **与 v1.0 的根本差异**：v1.0 的中心是"本回合怎么打"；v2.0 的中心是"这整场准备怎么赢，本回合只是路线上的一个节点"。

## 1. 设计哲学的升级

### 1.1 v1.0 的根本局限

v1.0 的战略层本质上是一个**分类器**：读取当前局面 → 贴一个标签（BURST / CHARGE / DEFENSE 等）→ 按标签执行规则。

这个模型的问题不是规则写得不够好，而是抽象层级错了：

- 它永远在"反应"，永远是当前帧的最优解，而不是全局路线的当前步骤
- BOSS / DEFENSE / BURST / CHARGE 本来就不是同一维度的东西，放进同一个枚举会互相覆盖信息
- 它不知道"这个技能要留到第三波"，不知道"这个从者可以卖掉"，不知道"这条破防条先不打"

**顶尖玩家的真实思维模式**是：先规划整场路线，然后在每个节点执行路线规定的动作，遇到偏差时修正路线。本回合的决策是路线的产物，而不是对当前局面的临时反应。

### 1.2 v2.0 的三个升级支柱

**支柱一：从单标签到多轴状态**  
局面不是一个标签，而是多个维度的同时描述。遭遇类型、威胁等级、资源状态、当前路线阶段是四件独立的事，必须同时存在于系统的认知里。

**支柱二：从回合内反应到波次级规划**  
在回合决策之上，增加第 0 层：战前建模与波次资源分配。这一层输出的不是"当前怎么打"，而是"整场怎么赢"的资源分配计划。

**支柱三：从固定操作顺序到前置动作图搜索**  
打卡之前的所有操作（从者技能、御主技能、换人）不是固定桶，而是一个合法序列搜索问题。搜索空间有约束，但顺序本身是决策对象，而不是预设答案。

### 1.3 什么保持不变

- 分层架构的方向是对的，仍然保留，但从 3 层变为 4 层
- 可解释性原则不变：每个决策都必须能说清理由
- 规则骨架优先于学习器的顺序不变

### 2.2 各层的核心职责边界

| 层级 | 核心问题 | 更新频率 | 不负责 |
|------|----------|----------|--------|
| 第 0 层 | "整场怎么赢" | 战前 + 每波次开始 | 不决定回合内操作 |
| 第 1 层 | "现在局面是什么" | 每回合 | 不决定目标 |
| 第 2 层 | "本回合要达成什么" | 每回合 | 不决定具体操作 |
| 第 3 层 | "具体怎么操作" | 每回合 | 不判断全局局势 |

## 3. 第 0 层：遭遇建模与波次规划

### 3.1 这一层解决什么问题

FGO 的大量标准打法在战斗开始之前就已经确定了资源分配方案：

- 第一波谁开充能技能、谁发 NP
- 第二波的主力什么时候换入
- 第三波哪几个从者 NP 同时爆发
- 哪个技能必须留到 BOSS 波才用
- 前排辅助完成任务后通过什么方式退出

这些不是回合内临时反应的产物，而是战前规划的产物。AI 必须有能力做这种规划，否则永远停留在"聪明但没计划"的层级。

### 3.2 遭遇建模：读取已知信息

在战斗开始前，系统需要建立对这场战斗的认知：

**队伍信息**
- 6 名从者的完整能力档案（技能、NP 类型、卡池、属性）
- 礼装效果（充能量、特殊技能、场地效果）
- 御主技能的可用状态

**遭遇信息**（来自遭遇脚本引擎，见第 11 节）
- 波次数量与各波敌人构成
- 各 BOSS 的破防条数量与触发效果
- 已知的特殊规则（技能封印、御主技封印、场地效果、轮换脚本）
- 各波次的威胁评级

**历史信息**（可选，用于提升准确性）
- 该遭遇的已知最优路线
- 相似队伍的成功方案

### 3.3 BattlePlan：波次资源分配方案

这是第 0 层的核心输出，描述整场战斗的资源使用计划：

```
BattlePlan
│
├── WaypointSchedule（关键节点时间表）
│   ├── Wave 1
│   │   ├── 主要输出手段：前排 A 的 NP（当前充能 80%，需开充能技能）
│   │   ├── 关键技能使用：从者 B 的充能技能 → 从者 A 的攻击强化 → A 放 NP
│   │   └── 预期退出人员：从者 C（技能交完后 Order Change 换下）
│   ├── Wave 2
│   │   ├── 主要输出手段：从者 D 的 NP（换入后立即发动）
│   │   ├── 关键技能使用：御主 NP 充能 → D 的攻击强化 → D 放 NP
│   │   └── 预留要求：从者 E 的保命技能不得在此波使用
│   └── Wave 3（BOSS）
│       ├── 爆发节点 1：第 1 破防条，从者 E + F 双 NP
│       ├── 爆发节点 2：第 2 破防条，御主攻击强化 + E 的最后技能
│       └── 风险节点：BOSS 第 3 回合放 NP，需提前部署无敌
│
├── ResourceReservation（资源预留清单）
│   ├── 必须留到 Wave 3 的技能：从者 E 的无敌技能
│   ├── 必须留到 Break 2 的技能：从者 F 的攻击强化
│   └── 御主技能分配：充能技能用于 Wave 2，攻击强化用于 Wave 3
│
├── ProtectedSet（必须存活的人 + 存活到何时）
│   ├── 从者 E：必须存活到 Wave 3 Break 1 结束
│   └── 从者 F：必须存活到 Wave 3 结束
│
├── ExpendableSet（可以牺牲的人 + 牺牲时机）
│   ├── 从者 C：Wave 1 结束后可通过 Order Change 退场
│   └── 从者 A：Wave 2 结束前若 HP 过低可接受死亡
│
└── FallbackPlan（偏差修正预案）
    ├── 若 Wave 1 未能清场：追加 Arts 链蓄 NP，延迟一回合清场
    ├── 若 Wave 2 从者 D 死亡：从者 G 接替输出，御主攻击强化改给 G
    └── 若 BOSS 阶段 NP 未就绪：转为 Buster 链输出消耗，等下一轮充能
```

### 3.4 BattlePlan 的生成逻辑

生成 BattlePlan 的思路是**从终点倒推**：

1. 确定最终 BOSS 波需要什么资源（哪几个从者的 NP，哪些关键技能）
2. 往前推算这些资源需要多少回合积累
3. 确定中间波次的主要任务（快速清场，或同时蓄 NP）
4. 识别可以提前交技能的从者，规划其退场时机
5. 评估风险节点（敌人 NP 放出时机），提前预留防御资源

### 3.5 BattlePlan 的更新时机

BattlePlan 不是一次性生成后固定不变的。它在以下时机更新：

| 时机 | 更新原因 | 更新范围 |
|------|----------|----------|
| 战前 | 初始规划 | 全部 |
| 每波开始 | 前波结果确认，资源实际消耗确认 | 当前波及之后 |
| 破防条触发 | 进入下一破防阶段，脚本变化 | 当前 BOSS 战 |
| 重大偏差出现 | 关键从者死亡、资源严重损耗 | 激活 FallbackPlan |

## 4. 第 1 层：多轴局面状态分解

### 4.1 为什么要多轴

v1.0 用单标签（BOSS / DEFENSE / BURST 等）描述局面，会导致信息覆盖。  
例如：最终波 + 有破防条 + 敌人下回合放 NP + 己方主 C NP 满 + 辅助准备换下，这个局面在单标签系统里只能选一个标签，而真正的处理方式需要同时考虑所有维度。

多轴状态的核心思想：**这些维度本来就应该同时存在，不应该互相覆盖。**

### 4.2 五轴状态向量

**轴一：遭遇轴（Encounter Axis）**  
描述当前面对的是什么类型的战斗节点。

| 状态值 | 含义 |
|--------|------|
| 普通波次 | 没有 BOSS，正常小兵 |
| BOSS 初始 | BOSS 第一条 HP Bar |
| BOSS 破防中（第 N 条） | 已打穿 N-1 条，当前在第 N 条 |
| 破防条临界 | 当前 HP Bar 可在本回合打穿 |
| 波次清尾 | 本波所有敌人可在本回合全部消灭 |
| 脚本触发阶段 | 遭遇脚本的特殊阶段（见第 11 节） |

---

**轴二：威胁轴（Threat Axis）**  
描述当前己方面临的生存压力等级。

| 状态值 | 判定条件 |
|--------|----------|
| 安全 | 无人濒死，敌人 NP 充能 < 50% |
| 受压 | 有人 HP < 50%，或敌人 NP 充能 > 70% |
| 致命 | 有人 HP < 20%，或敌人本回合放 NP 且有人会被击杀 |
| 灭队风险 | ProtectedSet 中有人面临致命威胁 |

---

**轴三：资源轴（Resource Axis）**  
描述当前己方的输出资源积累状态。

| 状态值 | 含义 |
|--------|------|
| 资源枯竭 | 无 NP 可用，技能全 CD，无暴击星 |
| 蓄力中 | 正在积累 NP / 星，未到爆发点 |
| 爆发就绪 | 计划中的爆发从者 NP 已满，关键 Buff 技能可用 |
| 过充状态 | NP 超过 100%（Over Charge 层数有意义） |
| 回收回合 | 本回合主要任务是在输出的同时回收 NP 为下轮准备 |

---

**轴四：路线轴（Route Axis）**  
描述当前正在执行的是哪种战术路线，与 BattlePlan 的 WaypointSchedule 对应。

| 状态值 | 含义 |
|--------|------|
| 按计划推进 | 当前状态与 BattlePlan 预期一致 |
| 加速推进 | 资源比预期更充裕，可以提前爆发 |
| 延迟补救 | 前回合偏差，当前需要补蓄资源 |
| 路线变更 | 触发 FallbackPlan，执行备选路线 |
| 波次收尾 | 当前波即将结束，准备下波交接 |

---

**轴五：牌堆轴（Deck Axis）**  
描述当前牌堆状态，是指令卡决策的重要上下文。

| 信息项 | 说明 |
|--------|------|
| 当前牌堆周期 | 15 张卡（3 人各 5 张）按抽取周期循环，记录已抽位置 |
| 本回合已抽位置 | 当前 5 张手牌在周期中的位置 |
| 剩余关键卡分布 | 周期内还剩几张 Arts / Buster / Quick |
| 洗牌触发预期 | 本波内是否会触发 Command Shuffle / 从者死亡导致的重置 |
| 周期剩余回合 | 当前周期还有几回合耗尽，影响下回合手牌预测 |

### 4.3 偏差分析：LocalDeviation

第 1 层除了输出 SituationState，还要输出当前局面与 BattlePlan 的偏差分析：

```
LocalDeviation
├── 资源偏差：当前 NP / 技能状态与计划预期的差距
│   例："主 C NP 比预期少 20%，需要额外一回合 Arts 链"
├── 人员偏差：ProtectedSet 中是否有人状态异常
│   例："从者 E 比预期损耗更多 HP，需要提前部署保命"
├── 时序偏差：当前波次是否比预期多用了回合
│   例："Wave 2 已用 3 回合仍未清场，御主充能需提前使用"
└── 脚本偏差：遭遇脚本触发了非预期效果
    例："BOSS Break 后额外追加了充能，NP 比预计早一回合"
```

## 5. 第 2 层：本回合目标编译

### 5.1 目标编译的输入

第 2 层接收三个输入：
- **SituationState**：当前多轴局面
- **BattlePlan**：整场规划（当前节点的期望状态）
- **LocalDeviation**：当前与计划的偏差

目标编译的核心工作是：**结合当前局面和计划偏差，决定本回合最需要做什么。**

### 5.2 本回合目标的结构

```
TurnObjective
├── PrimaryGoal（主目标）：本回合必须优先完成的核心任务，唯一
├── SecondaryGoals（次目标列表）：在不影响主目标前提下顺带完成
├── Constraints（约束条件）：绝对不能违反的底线
│   ├── ProtectedSet 约束：某从者本回合不得承受致命伤害
│   ├── ResourceReservation 约束：某技能本回合不得使用
│   └── BreakTiming 约束：某条破防条本回合不得打穿 / 必须打穿
└── PreferredTarget（优先攻击目标）：本回合集中输出的敌人索引
```

### 5.3 目标编译规则

目标编译是多轴状态的综合判断，而不是简单的优先级覆盖。以下是核心编译规则：

---

**规则组 A：威胁轴主导的目标（灭队风险时）**

当威胁轴为"灭队风险"时：
- 主目标强制为"解除 ProtectedSet 成员的致命威胁"
- 这是唯一会强制覆盖路线轴的情况
- 但如果当前资源轴为"爆发就绪"，且爆发本身能消灭威胁来源（打死敌人），则允许通过爆发同时解决威胁

---

**规则组 B：遭遇轴 × 资源轴的交叉判断**

这是最常见的非紧急情况，需要交叉判断：

| 遭遇轴 | 资源轴 | 主目标 |
|--------|--------|--------|
| BOSS 破防条临界 | 爆发就绪 | 打穿破防条（同时触发爆发） |
| BOSS 破防条临界 | 蓄力中 | 视破防条剩余 HP 决定：能打穿则打穿，不能则蓄力 |
| 波次清尾 | 任意 | 最小资源消耗清场（优先保留高 CD 技能给下波） |
| 普通波次 | 蓄力中 | 最大化 NP 充能（Arts 链优先） |
| 普通波次 | 爆发就绪 | 评估是否提前爆发：若能一回合清场，爆发；否则继续蓄 |
| BOSS 初始 | 蓄力中 | 蓄力同时施加减防/控制 Debuff |
| BOSS 初始 | 爆发就绪 | 全力爆发，优先使用攻击 Buff 技能 |

---

**规则组 C：路线轴偏差修正**

当路线轴显示偏差时，主目标受到修正：

- **资源比预期充裕（加速推进）**：主目标可提前执行下一波次的计划节点
- **资源比预期不足（延迟补救）**：主目标加入"补充缺失资源"的分量，推迟非必要的高消耗操作
- **路线变更（FallbackPlan 激活）**：主目标由 FallbackPlan 的当前步骤决定

---

**规则组 D：约束条件的来源**

约束条件由 BattlePlan 的 ResourceReservation 和 ProtectedSet 直接映射：

- 标记为"必须留到 Wave 3"的技能 → Constraints 里加入"不得使用该技能"
- ProtectedSet 中的从者 → Constraints 里加入"不得让该从者在本回合死亡"
- 标记为"不得提前打穿"的破防条 → Constraints 里加入 BreakTiming 约束

## 6. 第 3 层：前置动作图搜索与执行

### 6.1 根本性的设计变更

v1.0 把打卡之前的操作分成了固定的桶并按固定顺序执行：

```
v1.0（错误）：换人 → 御主技能 → 从者技能 → 打卡
```

这个顺序作为"一般情况说明"可以，但作为系统约束是错误的。

原因：Order Change 是一种 Master Skill，属于战斗准备窗口的一部分。实际的最优操作序列中，经常出现：

```
现实最优序列示例：
前排辅助开全部技能 → Order Change 换出辅助 → 后排新辅助进场 → 新辅助开技能 → 打卡
```

如果把换人锁死在第一步，这整类最优路线会被系统结构直接废掉。

### 6.2 统一前置动作窗口

打卡之前的所有操作统一进入一个**前置动作窗口（Pre-Attack Window）**，在这个窗口内的所有操作都是可搜索的决策对象：

```
Pre-Attack Window（前置动作窗口）
├── 可用动作集合
│   ├── ServantSkill（从者技能，最多 9 个，按可用性筛选）
│   ├── MasterSkill（御主技能，最多 3 个，按可用性筛选）
│   └── OrderChange（换人，按可用性筛选）
│
├── 合法性约束
│   ├── 换人只能在当前时间窗口执行一次
│   ├── 每个技能只能使用一次
│   ├── 换人后场上人员更新，后续技能集合随之更新
│   └── Constraints 中的禁用技能不可选
│
└── 搜索目标
    └── 找出满足约束的前置动作序列，使得打卡时的局面价值最大化
```

### 6.3 前置动作序列的价值评估

如何判断"打卡时的局面价值最大化"？评估打卡前局面的价值，需要考虑：

- 当前所有 Buff 状态（技能效果已叠加）
- 是否有 NP 可用，NP 充能量
- 当前暴击星数量
- 前排人员构成（换人后可能变化）

前置动作图的搜索不需要枚举所有排列（成本过高），而是按以下约束剪枝：

**剪枝规则一：技能顺序的语义约束**  
有些技能顺序存在语义依赖，不是所有排列都有意义：
- NP 充能技能必须在 NP 发动之前（打卡之前）
- 攻击强化必须在对应的伤害输出之前
- 控制技能（眩晕）若用于打断敌人 NP，必须在本回合结束前生效

**剪枝规则二：换人的时机约束**  
换人的时机决定了"哪些技能属于哪批人"：
- 换人之前只有原前排的技能可用
- 换人之后新进场从者的技能才可用
- 若目的是"前排交完技能再换下"，换人必须放在该从者技能之后

**剪枝规则三：无效动作排除**  
满足以下条件的技能不进入搜索空间：
- 在 Constraints 里被标记为本回合禁用
- 效果与当前目标完全无关（如当前主目标是生存，星生成技能不进入搜索）
- 当前已有同效果且仍有剩余回合的 Buff，且叠加收益低于使用阈值

### 6.4 前置动作序列的输出格式

```
PreAttackActionSequence（有序列表）
├── 动作 1：从者 C 释放技能 2（目标：从者 A，效果：NP 充能 +30%）
├── 动作 2：从者 C 释放技能 3（目标：自身，效果：攻击 UP 3 回合）
├── 动作 3：Order Change（换出：从者 C，换入：从者 D）
├── 动作 4：御主技能 1（目标：从者 A，效果：NP 充能 +20%）
├── 动作 5：从者 A 释放技能 1（目标：自身，效果：Buster UP + NP 威力 UP）
└── [进入打卡阶段]
```

## 7. 技能决策子系统（重构）

### 7.1 技能子系统的新定位

技能子系统不再是独立的决策模块，而是前置动作图搜索的**评估函数提供者**。它的职责是：

1. 判断每个可用技能的本回合使用价值
2. 识别技能之间的顺序依赖关系
3. 提供"技能使用阈值"供搜索剪枝使用

### 7.2 技能价值的三个维度

**维度一：即时价值**  
技能效果直接作用于本回合决策的价值。

- NP 充能技能：用后能否触达 100%？触达的回合价值是什么？
- 攻击强化：本回合是否有配套的 NP 或暴击输出来消耗这个 Buff？
- 控制技能：敌人 NP 充能是否接近满，本回合控制能否打断？

**维度二：机会成本**  
技能有冷却时间，"现在用"意味着"未来特定回合不可用"。必须与 BattlePlan 的 ResourceReservation 对照：

- 若该技能被标记为"必须留到 Wave 3"，当前波次的即时价值再高也不能用
- 若该技能没有预留约束，且下一次关键节点在其冷却结束之后，则可以使用

**维度三：协同放大效果**  
技能与其他技能、与 NP、与指令卡的协同关系：

- 攻击强化 + NP 发动 = 强协同，价值是两者单独价值的乘积
- NP 充能 + 攻击强化 + NP 发动 = 三件套，排序固定且价值最高
- 星生成技能 + Quick 链 + 聚星技能 = 暴击流三件套

### 7.3 技能分类与决策规则（重构版）

---

**A 类：生存技能（无敌、回避、Guts 主动激活）**

核心原则：机会成本极高，只在"不用必死"时触发，或被 BattlePlan 指定为当前节点的必用资源。

使用条件：
- 威胁轴为"致命"或"灭队风险"，且该从者在 ProtectedSet 中
- 或 BattlePlan 的 WaypointSchedule 明确指定本节点使用
- 或遭遇脚本标注了"本回合敌人有必中全体伤害且伤害量 > 当前最低 HP 从者 HP"

不使用条件：
- 威胁轴为"受压"但不到"致命"，且当前 ExpendableSet 的从者在受威胁（可以接受其死亡）
- 技能被 ResourceReservation 标注为预留

---

**B 类：控制技能（眩晕、魅惑、封印）**

最高价值场景：
- 敌人 NP 充能即将满（本回合或下回合放 NP），眩晕可直接打断
- BOSS 脚本阶段，眩晕可跳过一个脚本触发节点

普通场景不建议使用（机会成本 > 普通收益）。

---

**C 类：输出强化技能（攻击 UP、卡色强化、NP 威力 UP、暴击强化）**

核心判断：**必须有配套的输出动作在本回合消耗这个 Buff**，否则 Buff 可能在下回合自然消失（1 回合 Buff），或虽然持续多回合但不如在爆发节点使用。

配套判断优先级：
1. 本回合资源轴为"爆发就绪" → 强烈建议使用
2. 本回合主目标是"打穿破防条" → 建议使用
3. 没有配套输出但 Buff 持续 3 回合以上，且下一个爆发节点在 3 回合内 → 可以使用
4. 其他情况 → 等待更好时机

关于叠加的正确逻辑：**"已有同类 Buff"不意味着不应该叠加**。正确判断是：再叠一次，能否跨越伤害断点（恰好击杀）、回收断点（NP 刚好够 100%）或破防断点（HP 刚好够打穿）？如果能，叠加就是值得的。

---

**D 类：NP 充能技能**

价值评估要点：
- 用后 NP 能否达到 100%？能达到则本回合使用，配合 NP 发动
- 用后 NP 在 70%~99%？可以使用，加速下回合满充
- 用后 NP 不足 70%？延迟使用，等 NP 自然充能后再补

特殊情况：若当前路线轴为"延迟补救"（资源比预期少），且这是本波次唯一充能来源，则即便效率偏低也应使用。

---

**E 类：治疗技能**

阈值触发规则：
- HP 低于 30%（濒死阈值） → 立即触发，无论其他条件
- HP 在 30%~50% 且当前威胁轴为"受压" → 触发
- HP 在 50% 以上 → 延迟，保留治疗时机给更需要的时刻

**拥有 Guts 效果的从者**：Guts 存在时，该从者的濒死阈值放宽。Guts 是"让一次死亡变成 HP=1"，不是无敌，处于 Guts 激活状态下的从者仍然需要在触发后获得治疗，否则下一击致死。

---

**F 类：星生成 / 聚星技能**

使用条件：
- 当前路线节点为"暴击流回合"（BattlePlan 明确规划了本回合暴击输出）
- 或当前暴击星数量充足（20 颗以上）且有从者拥有高聚星率，本回合打暴击收益显著

---

### 7.4 技能的目标选择

**友方目标**
- 攻击强化 → 本回合的主要输出从者（NP 满了或本回合暴击主力）
- NP 充能 → 距离 100% 最近的 ProtectedSet 中的主要输出从者
- 治疗 → HP 百分比最低的 ProtectedSet 中的从者
- 聚星 → 本回合暴击主力

**敌方目标**
- 控制 / 眩晕 → NP 充能最高的敌人（优先打断 NP）
- 减防 / 攻击 DOWN → HP 最高的敌人（最大化减防收益）

## 8. 指令卡决策子系统（重构）

### 8.1 选卡决策的正确输入时机

选卡评分必须在**所有前置动作（技能和换人）执行之后**进行，因为技能效果（Buff）已经改变了每张卡的实际价值。

如果在技能执行前就对卡打分，攻击强化的效果无法被计入，伤害估算会严重偏低。

### 8.2 动作空间的完整定义

v1.0 把手牌理解为"5 张卡选 3 张，最多 60 种排列"。这个定义在有 NP 可用时是不完整的。

完整的选卡动作空间：

```
当前回合可打出的"卡"类型
├── 普通指令卡（来自 5 张手牌）
│   ├── 归属于前排从者的 Buster / Arts / Quick 卡
│   └── 共 5 张，按发牌周期分配
└── NP 卡（不来自手牌，独立存在）
    └── 每个 NP ≥ 100% 的前排从者各有一张 NP 卡可打出

最终打出 3 步，每步可以是普通卡或 NP 卡
```

因此当有 1 个从者 NP 满时，动作空间是：从 5 张普通卡 + 1 张 NP 中选 3 步的全排列，规模显著大于 60。有多个 NP 满时，动作空间进一步扩大。

### 8.3 三步操作序列的评分框架

对于每一种合法的三步操作序列（card1 → card2 → card3），其总价值由以下部分合成：

**首卡加成价值**  
第一步打出的卡类型，决定本回合对所有后续卡有效的首卡加成：

| 首卡类型 | 加成效果 | 推荐阶段 |
|----------|----------|----------|
| Buster | 全回合伤害基础乘区提升 | 爆发、BOSS |
| Arts | 全回合 NP 获取率提升 | 蓄力 |
| Quick | 全回合暴击星生成率提升 | 蓄星 |
| NP 卡作为首卡 | NP 自身享受首卡加成，后续普通卡也享受 NP 卡类型对应的首卡加成 | 取决于 NP 卡色 |

**各步单卡价值之和**（含首卡加成影响后的重新估算）

**同色链加成**（若三步同色）：

| 链类型 | 效果 | 说明 |
|--------|------|------|
| Buster 链 | 整链伤害乘区提升 | 整体伤害加成，非"首卡额外打一次" |
| Arts 链 | 整链 NP 获取大幅提升 | 包含首卡 Arts 加成在内的叠加 |
| Quick 链 | 整链暴击星生成大幅提升 | 含 Quick 首卡加成 |

**Brave Chain 加成**（若三步属于同一从者）：
- 额外追加一次 Extra Attack
- Extra Attack 不是"通常为全体 AoE"——默认情况下 Extra Attack 的攻击范围由机制决定，某些效果会改变 Extra Attack 的范围为 AoE，这是特殊情况而非默认
- Extra Attack 享受本回合的首卡加成，且若同时触发了同色链，Extra Attack 也享受对应的链加成
- Brave Chain 等同于多获得一次完整的 Extra Attack 输出机会

**Overkill 转火逻辑**：
- 某目标死亡后，如果后续操作归属于同一从者，伤害继续对死亡目标进行 Overkill 结算（NP 继续回收、暴击星继续生成）
- 如果后续操作归属于不同从者，伤害转移至下一个存活目标
- 这个差异对 NP 回收量和星生成量有显著影响，在估算时必须按实际目标状态计算

### 8.4 单卡价值的权重体系（修订版）

每张卡的价值由三个维度合成，权重由当前**多轴局面状态**共同决定（而非单一阶段标签）：

| 价值维度 | 影响因素 |
|----------|----------|
| 伤害价值 | 资源轴（爆发就绪时权重高）、遭遇轴（BOSS 阶段权重高）、Buff 状态 |
| NP 充能价值 | 资源轴（蓄力中时权重高）、与 100% 的距离（越近价值越高） |
| 暴击星价值 | BattlePlan 是否规划了下回合暴击输出、当前星数量（已很多时边际价值低）|

权重不是固定表格，而是由多轴状态实时计算的连续值。

### 8.5 牌堆周期对选卡决策的影响

牌堆轴的信息直接影响选卡决策：

**当周期即将耗尽（本回合或下回合会重置）**：
- 当前手牌中的卡是本周期最后几张，不需要"留着"给下回合
- 可以更积极地使用当前手牌，因为下回合会重新发牌

**当周期刚刚重置（刚经历了洗牌或从者死亡重置）**：
- 手牌分布已重置，之前的记牌信息作废
- 需要重新建立牌堆跟踪

**Command Shuffle 的使用时机**：
- Command Shuffle 不是"运气操作"，而是重置当前牌堆周期的主动工具
- 当当前手牌极差（没有所需颜色）且资源轴为"蓄力中"时，Command Shuffle 是合理选择
- Command Shuffle 后的牌堆周期重置，需要重新进行牌堆跟踪

## 9. Buff 语义模型（升级）

### 9.1 为什么 Buff 管理需要升级

v1.0 的 Buff 管理是"按效果名分类，判断是否已有同类"。这只够支撑入门级决策。

顶尖决策中，Buff 的以下属性会直接影响决策质量：

- **乘区归属**：两个"攻击 UP" Buff 如果在同一乘区，叠加效果是相加；若在不同乘区，叠加效果是相乘（价值更高）
- **生效时序**：Buff 是在伤害计算前生效（乘入伤害公式）还是在攻击后生效（回 NP、生星）
- **持续方式**：按回合持续 vs. 按次数持续，两种持续方式的"剩余价值"计算方式不同
- **作用窗口**：只作用于普通卡、只作用于 NP、只作用于暴击，还是通用

### 9.2 Buff 的完整语义描述

每个 Buff 需要记录以下语义信息：

```
Buff 语义描述
├── 效果类型：攻击 UP / 防御 DOWN / NP 获取 UP / 暴击伤害 UP / ...
├── 效果数值：+30%、-20% 等
├── 乘区标识：A 乘区 / B 乘区 / C 乘区（决定叠加是加算还是乘算）
├── 生效时序：打前（前置）/ 打后（后置）/ on-attack / on-hit
├── 持续方式：N 回合 / N 次 / 永久
├── 剩余计数：当前还剩几回合或几次
├── 作用窗口：普通卡 / NP / 暴击 / Extra / 全部
└── 叠加规则：可叠加（同乘区相加）/ 不可叠加（取最高值）
```

### 9.3 乘区概念对决策的影响

**相同乘区的叠加（加算）**：  
两个同乘区的攻击 UP Buff，+30% 和 +20% 叠加后效果是 +50%，乘入基础伤害。

**不同乘区的叠加（乘算）**：  
+30% 攻击 UP 和 +20% 卡色强化在不同乘区时，叠加效果是 1.3 × 1.2 = 1.56，等效于 +56%，显著高于同乘区的 +50%。

**对技能决策的影响**：  
判断是否叠加同类 Buff 时，不应该只看"是否已有同类"，而应该看：
- 新 Buff 与已有 Buff 是否在同一乘区（加算 vs. 乘算决定叠加收益）
- 叠加后能否跨越伤害断点、回收断点、破防断点
- 如果叠加收益能跨越关键断点，即便同乘区的"效率递减"也值得叠加

### 9.4 持续方式对决策的影响

**按回合持续的 Buff**（如"攻击 UP 3 回合"）：
- 在爆发节点使用收益最高（每回合都有高强度消耗）
- 在蓄力回合使用，部分持续时间被"浪费"在低伤害回合

**按次数持续的 Buff**（如"NP 威力 UP 1 次"）：
- 只有在 NP 发动的那一刻才会消耗
- 可以提前开，不会因为蓄力回合而损失
- 决策规则：NP 威力 UP（1 次）可以在 NP 发动前任意时刻开，不需要严格等到"同回合"

## 10. 伤害与收益估算（升级）

### 10.1 估算精度的分级

不同决策需要不同精度的估算：

| 估算场景 | 需要的精度 | 使用方式 |
|----------|-----------|----------|
| 比较卡组合的相对优劣 | 近似估算（误差 20% 以内可接受） | 用于快速筛选，排除明显劣选项 |
| 判断是否能本回合秒杀目标 | 较高精度（误差 10% 以内） | 用于决定是否需要追加输出 |
| 判断能否打穿破防条 | 高精度（误差 5% 以内） | 用于决定破防时机，误差大会导致"差一点打穿"的浪费 |
| 判断 NP 回收量能否回满 | 高精度 | 用于 Arts 循环 / Quick 循环路线的可行性判断 |

### 10.2 局部精确模拟器

对于需要高精度的判断场景，v2.0 引入**局部精确模拟器（Local Simulator）**：

局部精确模拟器的设计原则：
- 范围限定在"本回合内"，不做跨回合推演（跨回合用价值函数估计代替）
- 模拟本回合所有前置动作执行后、打出指定卡组合后的完整状态
- 计算输出：最终伤害量、NP 回收量、暴击星生成量、目标存活状态

局部精确模拟器的使用场景：
- 破防条打穿判断（必须精确）
- 秒杀判断（必须精确）
- Arts 循环可行性验证（NP 回收量必须精确到能否再次达到 100%）
- 多 NP 爆发的顺序优化（NP 顺序影响后续普通卡的加成）

### 10.3 远期价值函数

对于超出"本回合"的收益，使用**远期价值函数估计**而非精确模拟：

远期价值函数评估的是：**当前操作的结果，对未来 N 回合的期望收益的贡献。**

| 近期操作 | 远期价值来源 |
|----------|-------------|
| 本回合 Arts 链多充 20% NP | 下回合 NP 可用的概率增加，折算为"提前 X 回合爆发"的价值 |
| 本回合 Quick 链多生 10 颗星 | 下回合暴击期望的增量 |
| 本回合换人换入后排 NP 满的从者 | 本回合额外一次 NP 爆发的价值 |
| 本回合提前使用了 ResourceReservation 中的技能 | 与 BattlePlan 产生偏差，计入负向远期成本 |

### 10.4 Overkill 与转火的精确计算

Overkill 和转火直接影响 NP 回收和星生成，在循环型路线中尤其关键：

**Overkill 结算规则**：
- 敌人 HP 归零后，同一从者继续攻击同一目标，仍然触发 Overkill 结算
- Overkill 结算中，NP 获取和暴击星生成按正常段数计算
- 敌人死亡后切换到其他从者，则不再触发 Overkill，伤害转移至下一目标

**对 NP 循环的影响**：
- 在 Arts 链目标死亡的情况下，后续 Arts 卡的 NP 回收量取决于是否有其他存活目标
- 如果清完场最后一张卡没有目标，该卡的 NP 回收量为 0
- 规划 Arts 循环时，必须考虑各卡击中目标时目标是否存活

<a id="s11"></a>
## 11. 遭遇脚本引擎

### 11.1 为什么需要遭遇脚本引擎

FGO 的高难副本不是"一堆例外情况的集合"，而是**脚本型对局**。每个高难副本都有自己的事件触发规则：

- 每隔 N 回合轮换的技能效果
- 破防条触发时的特殊反应
- 开局强制施加的场地效果
- 御主技能被封印的特定回合段
- BOSS HP 进入特定区间后的行动模式变化
- 每回合固定追加充能量

把这些写成"特殊情况补丁"，最终会变成无限增长的 if-else 链。正确的做法是建立事件钩子结构，让副本脚本通过标准接口挂载，而不是侵入核心逻辑。

### 11.2 遭遇脚本的事件钩子结构

```
EncounterScript（遭遇脚本）
│
├── on_battle_start
│   └── 战斗开始时执行：初始充能、场地效果、特殊规则声明
│       例："御主技能在前 3 回合被封印"
│       例："场地效果：所有 Buster 卡伤害 -50%"
│
├── on_wave_start(wave_n)
│   └── 指定波次开始时执行
│       例："Wave 3 开始时 BOSS 追加 Buff：攻击 +100%"
│
├── on_turn_start(turn_n)
│   └── 全局第 N 回合开始时执行
│       例："每 3 回合追加全体充能 20%"
│       例："第 5 回合开始 BOSS 获得无敌"
│
├── on_enemy_action(enemy_id, action_type)
│   └── 特定敌人执行特定类型行动时触发
│       例："BOSS 放 NP 后给自身追加 Buff：攻击 +200%（持续 3 回合）"
│
├── on_break(enemy_id, bar_index)
│   └── 特定敌人的第 N 条破防条被打穿时触发
│       例："Break 1 后：BOSS 追加 NP 充能 100%（立刻放 NP）"
│       例："Break 2 后：BOSS 获得永久攻击 UP"
│       例："Break 1 后：BOSS 变更 NP 伤害上限"
│
├── on_death(unit_id)
│   └── 指定单位死亡时触发
│       例："小兵 A 死亡时 BOSS 获得攻击 UP"
│
├── on_np_before_damage(enemy_id)
│   └── 敌人 NP 伤害计算前触发
│       例："BOSS 的 NP 在伤害前施加全体 Debuff"
│
├── on_np_after_damage(enemy_id)
│   └── 敌人 NP 伤害计算后触发
│       例："BOSS 的 NP 结算后追加回复效果"
│
└── on_turn_end(turn_n)
    └── 回合结束时触发
        例："每回合结束时全体扣除当前 HP 的 10%"
        例："每回合结束时全体 Poison 叠加 1 层"
```

### 11.3 遭遇脚本对 BattlePlan 的输入

第 0 层在生成 BattlePlan 时，会读取遭遇脚本的已知事件，将其作为规划约束：

- `on_break` 事件中的危险效果（如"Break 后 BOSS 立刻放 NP"）→ BattlePlan 在该 Break 前预留防御技能
- `on_turn_start` 中的封技回合 → ResourceReservation 中的御主技能禁用时间段
- `on_battle_start` 的场地效果（如 Buster 卡 -50%） → 调整 WaypointSchedule，将依赖 Buster 输出的节点替换为 Arts 或 Quick 路线

### 11.4 遭遇脚本对第 1 层状态的影响

第 1 层的遭遇轴需要感知当前是否处于脚本的特殊阶段：

```
遭遇轴扩展
├── 普通状态（无活跃脚本阶段）
├── 脚本特殊阶段 A：御主技封印中（前 N 回合）
├── 脚本特殊阶段 B：场地效果激活（特定卡色减伤）
├── 脚本特殊阶段 C：BOSS 强化形态（Break 后追加 Buff 阶段）
└── 脚本特殊阶段 D：轮换脚本阶段（BOSS 每 N 回合切换行动模式）
```

## 12. 计划约束系统

### 12.1 从"全员存活"到精确约束

v1.0 把"存活 > 输出 > 蓄力"作为全局铁律。这在入门教学中是对的，但在系统设计中过于绝对。

FGO 顶尖打法中，以下操作都是合理且常见的：
- 主动让前排辅助"卖掉"（通过 Order Change 退场，或接受其在任务完成后死亡）
- 用嘲讽位主动吃 BOSS 的 NP，牺牲一名从者换取整队存活
- 为了 3T 清场而接受非核心从者在某个时间点后死亡

这些操作在"全员存活优先"的框架里会被判断为错误，但在正确的约束框架里是最优选择。

### 12.2 三类约束的精确定义

**ProtectedSet（必须存活的集合）**
- 定义：必须存活到特定时间节点的从者列表，每个成员附带存活截止时点
- 来源：由 BattlePlan 在波次规划时确定
- 示例："从者 E 必须存活到 Wave 3 第二破防条结束后"
- 约束效果：ProtectedSet 中的成员面临致命威胁时，无条件触发最高优先级的保命措施

**ExpendableSet（可牺牲的集合）**
- 定义：在完成既定任务后可以接受死亡或退场的从者列表，每个成员附带"任务完成条件"
- 来源：由 BattlePlan 在波次规划时确定
- 示例："从者 C 在 Wave 1 结束后可通过 Order Change 退场"
- 示例："从者 A 在 Wave 2 的 NP 发动后，若 HP 不足则接受其死亡"
- 约束效果：ExpendableSet 成员面临威胁时，不触发保命措施，资源不为其浪费

**ResourceReservation（资源预留约束）**
- 定义：特定技能或御主技能被标记为"不得在某时刻之前使用"的约束列表
- 来源：由 BattlePlan 的波次规划确定
- 示例："从者 E 的技能 3（无敌）预留至 Wave 3"
- 约束效果：在约束生效期间内，对应技能不进入前置动作图的搜索空间

### 12.3 约束的动态更新

约束不是静态的，会随战斗进程更新：

| 触发条件 | 约束更新内容 |
|----------|-------------|
| ProtectedSet 成员完成了其关键任务 | 该成员移入 ExpendableSet |
| FallbackPlan 激活 | 重新评估 ProtectedSet 和 ResourceReservation |
| 关键从者意外死亡 | 重新规划剩余资源的 ProtectedSet |
| 破防条提前打穿 | ResourceReservation 中对应的"等待时机"约束提前解除 |

## 13. 各层信息流转

### 13.1 完整信息流图

```
─────────────────── 战前/波次开始 ───────────────────
队伍信息 + 遭遇脚本 → 第 0 层
                          │ BattlePlan（WaypointSchedule +
                          │ ProtectedSet + ExpendableSet +
                          │ ResourceReservation + FallbackPlan）
                          │
──────────────────── 每回合开始 ─────────────────────
实时游戏状态 + BattlePlan → 第 1 层（多轴状态分解）
遭遇脚本事件 ─────────────┘
                          │ SituationState（5 轴）
                          │ LocalDeviation（偏差分析）
                          │
SituationState            ↓
LocalDeviation  ─→  第 2 层（本回合目标编译）
BattlePlan ──────────────┘
                          │ TurnObjective（主目标 + 次目标 +
                          │ 约束条件 + 优先目标）
                          │
TurnObjective             ↓
实时游戏状态  ─→  第 3 层（前置动作图搜索）
                     │         │         │
                     ↓         ↓         ↓
              技能评估器   牌堆跟踪器   换人评估器
                     │         │         │
                     └────┬────┘         │
                          │              │
                     局部精确模拟器 ←────┘
                          │
                          ↓
                  PreAttackActionSequence
                  CardSelectionResult
                          │
                          ↓
                   操作执行（输出至游戏）
                          │
                          ↓
                   状态更新 → 反馈回第 0/1 层
```

### 13.2 BattlePlan 的传递与使用

BattlePlan 是跨层级的共享信息，各层的使用方式不同：

| 层级 | 使用 BattlePlan 的哪部分 | 用途 |
|------|--------------------------|------|
| 第 1 层 | WaypointSchedule（期望状态） | 生成 LocalDeviation（偏差分析） |
| 第 2 层 | 当前节点目标 + ProtectedSet + ResourceReservation | 生成目标约束 |
| 第 3 层 | ResourceReservation（禁用技能列表） | 前置动作搜索的剪枝约束 |

<a id="s14"></a>
## 14. 扩展设计

### 14.1 新遭遇副本的接入

新副本的特殊机制不再需要修改核心逻辑，只需要编写遭遇脚本：

1. 在遭遇脚本中声明所有事件钩子及其效果
2. 特殊约束通过标准字段（ResourceReservation、ProtectedSet 等）传入第 0 层
3. 场地效果通过事件钩子更新战斗状态，第 1 层状态感知自然接收

### 14.2 新从者机制的接入

部分新从者有非常规机制（如额外行动次数、条件触发的卡强化、特殊 NP 充能方式等）：

- 非常规被动效果：在从者状态模型中增加字段，在估算函数中增加对应分支
- 额外行动次数：在前置动作图的动作集合中增加对应的动作类型
- 特殊 NP 充能：修改 NP 获取率的计算逻辑，不影响决策框架

### 14.3 阵容风格感知

在 BattlePlan 的生成阶段，加入队伍风格识别，输出对应的路线偏好：

| 队伍风格 | 识别特征 | BattlePlan 倾向 |
|----------|----------|-----------------|
| Arts 循环 | 高 NP 获取率从者 + Arts 卡池为主 | WaypointSchedule 以 NP 循环为中心规划 |
| Quick 循环 | 高星生成 + 高聚星率从者 | WaypointSchedule 以暴击链循环为中心 |
| Buster 爆发 | 高攻击 UP Buff 辅助 + Buster 卡池 | 每 2~3 回合一次 Buster 爆发节点 |
| 控制拖延 | 大量控制技能 + 高持久性 | 以控制敌人行动为轴心，消耗战路线 |

## 15. 落地路线

### 15.1 四个迭代阶段

---

**第一阶段：建立第 0 层骨架**

目标：能够生成基础 BattlePlan，实现波次级资源预分配

具体内容：
- 实现 WaypointSchedule（3 波次的基础规划）
- 实现 ProtectedSet / ExpendableSet 的基础框架
- 实现 ResourceReservation（手动配置技能预留）
- 第 1 层暂时只输出简化的多轴状态（不含偏差分析）
- 第 2/3 层暂时继承 v1.0 的规则骨架

验收标准：AI 能按照预设计划，在正确的波次使用正确的技能，不在 Wave 1 用掉预留给 Wave 3 的技能

---

**第二阶段：升级第 1 层和第 2 层**

目标：多轴状态完整，本回合目标编译覆盖主要场景

具体内容：
- 完整实现 SituationState 的 5 轴
- 实现 LocalDeviation 偏差分析
- 第 2 层目标编译覆盖主要轴交叉场景
- 计划约束系统完整接入第 2 层

验收标准：AI 能在复杂局面（BOSS + 威胁 + 资源就绪同时出现）中做出正确的综合决策，不再因单一标签覆盖而做出错误选择

---

**第三阶段：重构第 3 层执行层**

目标：前置动作图搜索替代固定顺序，局部精确模拟器接入

具体内容：
- 实现前置动作图搜索（含合法序列约束和剪枝规则）
- 接入局部精确模拟器（优先覆盖破防条判断和秒杀判断）
- 完整的动作空间定义（含 NP 卡）
- 牌堆周期跟踪接入选卡子系统

验收标准：AI 能正确执行"前排辅助先交技能 → Order Change 换下 → 后排开技能"类路线，破防条判断准确率显著提升

---

**第四阶段：遭遇脚本引擎与高难支持**

目标：高难副本通过脚本接入，无需修改核心逻辑

具体内容：
- 完整实现遭遇脚本引擎的事件钩子结构
- 为主要高难副本编写遭遇脚本
- FallbackPlan 的生成与激活逻辑
- 远期价值函数的基础实现

验收标准：新副本只需编写遭遇脚本即可接入，核心模块不需要修改
